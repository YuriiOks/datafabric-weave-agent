Recommending reusable components: skills, MCP servers, agents

What the work is, how it is done day to day, and how the same method extends to data products and other component types.

Yurii Oksamytnyi · 3 September 2026 · for the Playbooks team and new joiners

The work in one sentence

Given a use case, tell the team what already exists that they can reuse — with evidence, or say clearly that nothing suitable exists.

Why it matters

The hub knows best-practice cards (use cases). The bank's reusable building blocks — skills, MCP servers, agents, knowledge sources — live in Agent Hub. Today nothing connects the two, so teams rebuild what exists.

What "recommendation" means here

Not a chat answer. A ranked, evidenced list of catalogue components per type, each with a fit verdict and two verbatim quotes — one from the component's record, one from the use case — that a reviewer can check in seconds.

Three deliverables: a validated registry of components, a recommendation service that cannot invent components, and a way to measure whether the recommendations are good.

How the work is organised

Six phases, each with a concrete artefact

1

Understand the sources

What each source holds, field by field. Artefact: a structural description with counts.

2

Validate the data

Find what is duplicated, missing, inconsistent or test noise. Artefact: a defect register with a rule per defect.

3

Build the registry

Derive identity, apply flags, record links, version it. Artefact: registry tables plus an ingest report.

4

Design the pipeline

Retrieval, assessment, verification, thresholds. Artefact: an architecture and a working proof of concept.

5

Measure

Golden set and metrics. Artefact: an evaluation report that states its own confidence.

6

Deliver

Hub pages, card panel, MCP tools. Artefact: a pull request and a manual test script.

Where we are

Phases 1–2 complete with numbers; phase 3–4 design complete and the proof-of-concept build under way; 5–6 scoped.

Why the order is fixed

A recommender built on unvalidated identifiers recommends the wrong thing confidently. Validation comes first, and it is the phase that produces the most reusable knowledge.

Phase 2 · output

Quality flags: visible, never silent

Blocking — component is not recommended until fixed

  • duplicate_id — the source identifier is shared with another record
  • name_description_mismatch — name and description name different systems
  • test_data — name or description matches test patterns
  • missing_frontmatter — skill file has no header block
  • raw_yaml_description — description is unparsed file content
  • empty_description

Informational — recorded, still eligible

  • no_version
  • folder_name_mismatch — folder differs from declared name
  • duplicate_name_across_folders
  • unresolved_dependency — a declared dependency matches nothing
  • spelling_variant — a known variant was normalised
  • nested_skill — skill file found below the expected depth

A flag is a fact about the source that anyone can see and act on. It is also the first draft of the validation rule the source should enforce itself.

What the ingest report shows

Counts per type (eligible / ineligible), the flag histogram, every unrecognised field with how often it appeared, unresolved links, and how skills were matched between the two sources. Counts only — never names or descriptions.

What it never contains

Owner or contributor identifiers, file paths, raw text of any record. The report is safe to share as-is.

Phase 4 · the design principle

The model selects from a list we give it. It never invents an identifier.

Rule 1

Enumerated candidates

Deterministic code retrieves at most eight candidates per type. The model refers to them by position, not by name.

Rule 2

One candidate per call

Each candidate is judged alone, so the model cannot trade candidates off or "improve" on the list.

Rule 3

Verified quotes

Every verdict carries two verbatim quotes. Code checks they really occur in the source text; if not, the verdict is discarded and counted.

Rule 4

Empty is a success

If nothing passes the threshold, the answer is "nothing suitable" with a reason — not the least-bad option.

Rule 5

Bounded synthesis

The final ordering step may reorder and explain; it is validated to return exactly the ids it was given.

Everything else — prompts, weights, thresholds — is a tunable. These five are not. They are what makes the output checkable by a business analyst without reading code.

Phase 4 · the pipeline

Six stages from use case to evidenced list

S1

Need profile

The use case is summarised into a controlled vocabulary: domains, capabilities, integrations, constraints. One model call.

S2

Retrieve

Three deterministic signals — keyword match, semantic similarity, and co-occurrence via agents that use the component — fused into a top list per type.

S3

Assess

One model call per candidate: fit strong / partial / none, two quotes, unmet preconditions, unknowns.

S4

Verify and score

Quotes checked by exact match; score from fit and retrieval; threshold applied; near-misses kept with reasons.

S5

Synthesise

Ordering and one-line rationale; validated to add or drop nothing.

S6

Present

Recommendations per type, near-misses, or an explicit empty result — each stamped with catalogue, prompt and model version.

Cost and speed bounds

At most eight assessments per type, four in parallel, thirty seconds each, cached on catalogue + prompt + model version. A typical run is under a minute and reproducible.

What is never stored or logged

The raw use-case text. Only its hash and length, the derived profile, and the short verified quotes are kept; logs carry stage names and counts.

Phase 5 · measure

How we know it works — and how we say what we do not know

Golden set (four kinds of case)

  • Positive: a real card with expected components, grounded where possible in agent-usage links (mechanical truth).
  • Empty control: synthetic needs with no plausible match; the right answer is "nothing".
  • Near-duplicate pair: two related cards; recommendations should overlap.
  • Stability: the same input three times; the top three must not change.

Metrics reported

  • Precision and recall at k per component type
  • False-positive rate on empty controls
  • Overlap on near-duplicate pairs; stability rate
  • Share of verdicts discarded because a quote did not verify; timeout rate

The honesty rule

Every golden case records who labelled it and with what confidence. Cases labelled by a drafting process rather than a person are marked as such, and the report says in its header that those numbers are not accuracy figures until a human confirms the labels. Confirming labels is a task a business analyst can own end to end.

Phase 6 · deliver

One service, two consumers

In the hub (people)

  • Recommend page: paste a use case or pick a card; results per type with evidence and near-misses.
  • Registry browser: every component with its flags, filters by type and flag, eligible-only by default.
  • Component detail: fields, flags explained, which agents use it, what it depends on.
  • Catalogue status: version, counts, flag histogram, unrecognised fields.
  • Card panel: "Suggested components" on each best-practice card.

As MCP tools (coding assistants)

  • check_duplicate — does a similar card already exist?
  • suggest_components — what could this use case reuse?
  • get_card — read one card by id.

The tool descriptions are written as routing guidance ("use this when…"), because a tool that is configured but never invoked adds nothing. Distribution, transport and authentication are platform concerns handled centrally, not in this work.

How the work looks day to day

A loop that always ends in a count

1

Read the source's structure

Sheet headers, file layout, field names, how existing code reads them. Never the content for its own sake.

→
2

Write a structure-only note

Field names, types, counts, examples with synthetic values. This is the knowledge that survives hand-over.

→
3

Propose a rule

"Identity is the folder name." "A row is test data when…" One sentence, falsifiable.

→
4

Run it over the whole corpus

Not a sample. A script or an agentic coding assistant applies the rule to every record and reports what it touched.

→
5

Report the count

"12 of 291." "0 mismatches after the fix." Then the rule goes into the registry code, with a test.

Tools

The bank's cloud workstation; the hub repository; the skills repository; the metadata export; an agentic coding assistant for corpus-wide checks and for building the proof of concept from a written architecture.

Working rules

Data never leaves the environment; findings are reported as structure and counts; every claim in a message has a number behind it; a fix is verified over the whole corpus before it is called a fix.

The loop, on a real case

A field that was empty on every card — and why

What was observed

The hub's card ingestion maps hand-written header keys to canonical names through a fixed alias table. A key that does not match falls through to a generic fallback and is stored under a name nothing reads. No error, no log line.

One instance was confirmed: the related-use-cases field was empty on all cards because the table expected a plural spelling and every card used the singular.

What was done

  • Alias added; re-run over the full corpus: 12 of 41 local cards now carry the field, 0 mismatches, 6 symmetric pairs.
  • Generalisable fix proposed: log a warning whenever the fallback produces a key no reader consumes.
  • The same class of defect is the leading hypothesis for the reported "capabilities present, completeness score zero" case; that field is being traced next.

The point of the example: the finding is a mechanism, not a symptom — and a mechanism produces a rule the new registry already applies to itself.

For new joiners · extending the method

Data products are a fourth component type, not a new system

The registry and the pipeline are type-agnostic. Adding a component type means answering five questions about its source; nothing in the recommendation stages changes.

1

Source of truth. Where is the authoritative list of data products, and what is the export or API that yields it? Structure it field by field before anything else.

2

Identity rule. Which field, or derived value, is the stable identifier? Assume the source's own ids are not unique until counted.

3

Quality flags. Which rows are test noise, incomplete, duplicated or inconsistent? Write each as a one-sentence rule and count what it matches.

4

Links. What connects a data product to agents or use cases — consumption records, lineage, ownership? Links are the strongest retrieval signal after text.

5

Vocabulary. Which controlled terms (domains, data kinds) let the need profile name what a data product provides? Add them to the shared vocabulary rather than inventing a parallel one.

For new joiners · a suggested first three weeks

Reproduce, own one rule, add one type

Week 1

Reproduce the counts

  • Read the structural notes and the defect register.
  • Run the registry ingest on the current export and repository; compare the ingest report to the recorded numbers.
  • Browse the registry pages; open ten flagged records and confirm the flag by eye.
Week 2

Own one rule end to end

  • Pick one quality flag or one source field with a known gap.
  • Tighten or add the rule, with a test using synthetic fixtures.
  • Re-run over the corpus; report the before/after count.
  • Confirm five golden-set labels and re-run the evaluation.
Week 3

Add a component type

  • Answer the five questions from the previous slide for the new source.
  • Write the reader and identity rule; register the type; ingest.
  • Add golden cases for the type; check the empty-control rate did not move.

Access needed

Cloud workstation; the hub repository and the skills repository; the current metadata export; the hub's model gateway (already configured by the hub); and, for data products, whatever holds their authoritative list.
