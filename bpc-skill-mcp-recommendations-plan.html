Decision framing

Approve the foundation and an honest boundary

01

Read this first to decide: what the scheduled baseline may claim, what the full engine adds, and what does not belong in recommendation scope.

Schedule correction. The 9–29 September extension is a conditional, authorised lexical baseline across all three types, with basic request/result interface wiring. It is not a commitment to semantic retrieval, model assessment, async runs, reviewer UI, graph boost or broad rollout. Those are later packages in this proposal, with no invented deadline.

Approve now

One internal, read-only service

Retain Postgres for catalogue lineage, policy, run state and evidence. Retain FalkorDB as a rebuildable source-graph projection. One logical service is consumed by existing internal surfaces; no public MCP endpoint is proposed.

Do not infer

Component fit from graph facts

Declared or observed source edges can explain provenance, prerequisite and readiness. They are never relevance labels. Existing Hub novelty and completeness describe an existing decision path, not semantic suitability for a new need.

Product boundary

A result informs review; it does not alter a system

03

Read this to prevent scope drift: recommendation returns information and records its basis. Execution remains an independently authorised workflow.

In scope

Find and explain

Discover eligible components, compare them to a need, disclose source/provenance, prerequisites and uncertainty.

Out of scope

Act on a result

Do not invoke an MCP server, run a Skill, create or attach an Agent, modify a card, graph or relationship, or follow links from component content.

Later decision

Knowledge sources

They need their own human-readable identity, eligibility and quality intake before becoming a fourth adapter.

Portal ID is not preselected as identity authority. Intake preserves source-owned IDs and aliases, then records a versioned resolution decision. A portal identifier may become an operational key only after the owner approves the mapping and scope. Ambiguous or quarantined records stay in a review ledger and never enter candidate membership.

Recommendation engine

Six stages; a model is confined to a bounded comparison

05

Read this for implementation: deterministic controls pin context, retrieve the eligible shortlist and validate the result; optional assessment can only compare the frozen set.

Membership control

The assessor never names a registry ID

It sees stable internal labels and opaque run-bound membership tokens. The server maps a valid token back to the candidate only after whole-batch validation.

Batch context

Bounded, type-specific comparison

All eligible evidence in the selected batch is supplied together. A batch is not cached row-by-row or stitched from partial model output.

A caller may ask for assessed mode only when release policy permits it; the service may return a typed unavailable outcome rather than downgrade silently. Baseline requests require need_profile=off: an optional model profile is rejected in baseline mode. In assessed mode, an optional model profile consumes only residual attempt capacity after every requested type has reserved its initial attempt. Baseline candidate payloads and assessed suggestion payloads are mutually exclusive. A baseline UI must never label its shortlist “recommended”. Each run returns exactly one outcome per requested type: an accepted run uses not_started/PENDING; a running type uses running/RUNNING; no eligible candidates means assessment_status=not_needed; a baseline candidate outcome is not_run; assessed completion follows whole-batch validation. Accepted and running runs omit payload. The one aggregation rule applies only after every requested type is terminal: a cancellation winning the fenced terminal compare-and-swap makes the run cancelled; otherwise all successful terminal types make it complete, a mix of successful and non-cancellation failed/unavailable types makes it partial, and no successful terminal type makes it failed. Until then, the run stays accepted or running. User-visible counts remain limited to the caller’s authorised scope; privileged inventory counts are internal or withheld.

baseline_observation

Candidate coverage, no fit claim

Shows retrieved candidates, lexical/exact trace, eligibility coverage and reason codes. It cannot claim suitability, semantic support, a final no-match, or a recommendation count.

assessed_recommendation

Suggestion for review, explicit origin

Shows model-assessed suggestions only when membership, current policy, exact source, material contradiction and prerequisite checks pass. It displays origin=model_assessment and not_independently_verified.

Request sequence

Idempotency recovers the original run before it sees newer data

07

Read this for recovery behavior: retries and replays preserve the original snapshot, scope and expiry instead of creating a newer answer under the same key.

Replay contract. After reauthorisation, the service looks up principal, scope and idempotency key before resolving a current card or publication. The same canonical payload recovers the original run and snapshot; a changed payload returns HTTP 409. While its bounded tombstone is retained, an expired key returns HTTP 410 and requires a fresh key. Once retention ends, the service deliberately cannot recognise that old key; post-retention reuse is a new submission with no idempotency guarantee.

The overall deadline is a durable absolute UTC expires_at. Each worker derives a conservative local monotonic remaining time from that expiry; restart, retry and handoff cannot reset the budget. Attempt ordinals, concurrency slots, leases and terminal compare-and-swap are durable across replicas.

Rollout and operating controls

Enable by evidence, with a visible off-switch

17

Read this to operate the service: a failed gate blocks or reverts the capability; it does not lower the definition of a result.

Observe

Generation, type outcome, invalid-handle, support failures, latency, attempts, cost and cache behavior.

Protect

Bound request size, candidate batches, model budget, policy version and retention. Retrieved text remains untrusted data.

Recover

Disable assessed mode, retain policy-approved baseline behavior and return unavailable rather than unverified data.

Retrieved descriptions and metadata are untrusted data. Typed packets, bounded context, policy rechecks and no-tool assessment reduce instruction-influence risk; output boundaries are enforced, but semantic robustness is not guaranteed. This follows OWASP prompt-injection guidance.

The assessed engine is five sequenced packages

R3–R7

R3–R7 are net-new and unscheduled. Vector work is an optional R4 channel; R5–R7 do not wait for it.

R3 — CandidateBatch and assessment decision contract
type CandidateBatch = {

  generation_id: string; ordered_members: CandidateMember[];

type NeedCitation = {
  card_id: string; original_field: string; card_version: string;

};
type ModelAssessmentDecision = {
  membership_token: string; fit: "strong" | "partial" | "none" | "abstain";

R3 inputs: R1/R2 frozen source/evaluation material and released model schema. Build: pinned context, one no-tool type batch, stable labels/run tokens, whole-batch validation and audit. The server maps token to its candidate, verifies each component span is inside that candidate’s allowed_component_citation_spans and matching field hash, and verifies every need citation against the original authorised card field, exact card version, span and field hash—not a profile or model inference. It then applies current policy, material-contradiction and mandatory-prerequisite checks. Output/handoff: Yurii provides the discriminated assessed envelope to Mayank’s evidence/UI seam. Acceptance: unknown token, cross-candidate citation, invalid span, unknown/unsupported claim, contradiction or unmet prerequisite withholds the affected suggestion; no partial batch rows are retained.

Every example includes the immutable run context and one type outcome for every requested type. The partial run exposes a completed assessed suggestion, a model failure and a withheld prerequisite without calling any of them a no-match. The cancelled run intentionally has no payload.

Attempt reservation. At assessed admission, reserve one initial assessment attempt for each requested type. An optional profile consumes only residual capacity; it cannot steal a type’s initial reservation. Three requested types plus a profile consume all four attempts and leave no retry. If the initial reservations cannot be made, reject assessed admission rather than start a run guaranteed to omit a requested type.

Evaluation disclosure — one contract, three separately judged recommendation types

Prerequisites: an authorised pinned publication, current policy, the existing R1/R2 lexical wrapper, named domain reviewers and a retention boundary. R1/R2 are existing inputs, not new full-engine work. Everything below is unscheduled and does not promise September delivery.

  1. Create separate Skill, MCP and Agent pools. Retain input/version, source/policy lineage, group, type, expected/forbidden IDs, evidence/prerequisite expectation, adjudicator and terminal outcome.
  2. Group related cards, aliases, duplicate MCPs, shared-source components and Agent configurations before development, validation and final splits. Pool all methods and domain nominations for blinded adjudication.
  3. Reviewers label relevant, partial, non-relevant or unjudged independently of relationships. Cover positives, hard negatives, valid empties, restrictions, missing text, duplicates, unknown prerequisites, source failures and fabricated or wrong-environment IDs per type.
  4. Freeze partial-credit policy and P@k before final testing. Report coverage, judged precision and qualified recall, empty false positives, forbidden hits, evidence/prerequisites, top-k stability/sensitivity, latency, attempts, tokens, cost, cache and outcome counts.

Artifact: versioned case, grouping, label, split and denominator manifests plus a per-type report. Acceptance requires all planned and unjudged/failure states to remain visible. Relationships, co-occurrence, model assertions and quote checks are evidence context, not independent semantic truth; failures never improve a denominator. Handoff: frozen inputs supply R3, R4, R6 and R7.

R3 — bounded source-constrained assessment, owned by Yurii

Prerequisites: R1/R2, frozen grouped validation cases, approved model gateway, source-excerpt/trace retention, current authorisation, label policy and request admission/cost limits. The lexical shortlist remains the only candidate authority.

  1. Bind each authorised lexical candidate to an opaque token and pin need, catalogue, policy and source versions. The model has no registry, graph or MCP tools and cannot nominate IDs.
  2. Build deterministic bounded excerpts with original anchors, requirements, constraints and omissions. If evidence cannot fit, mark the candidate unassessed or insufficient-evidence.
  3. Send one structured batch per requested type within the documented whole-request attempt, concurrency, deadline and token/cost envelope. A retry cannot consume another type's reserved work.
  4. Validate schema, token membership, duplicate/missing responses, citations, contradictions and prerequisites. Quote validity establishes attribution only; semantic support stays unreviewed until domain adjudication.
  5. Order by assessed class, actionability, unmet requirements, lexical rank and stable ID. Cache only validated assessments with complete lineage and reauthorise every hit.

Artifact: assessment schema, excerpt builder, verifier, budget/cache policy, replay fixtures and paired report. Acceptance requires truthful partial/unassessed counts and no forbidden-ID, access, evidence or prerequisite regression. Truncation, exhausted budget or invalid output is partial or failed, never complete-empty. Handoff: R5 consumes the selected result contract; failure leaves lexical baseline selectable.

R4 — optional retrieval experiments, owned by Yurii

Prerequisites: the R1/R2 frozen case/lineage contract, an agreed incumbent and a pre-registered per-type quality, safety, latency and cost ablation. This is optional, not a prerequisite for R5, R6 or R7; those packages work with lexical baseline when no experiment earns continuation.

  1. Qualify a policy-sensitive vector query on the deployed stack. It enforces scope before retrieval, retains embedding/text-builder/content-hash lineage and fails closed if unavailable.
  2. Compare lexical with lexical plus vector on unchanged held-out cases. Preserve channel ranks and stable ties; report each type, not just an aggregate.
  3. Only after vector earns continuation, compare fixed weighted fusion with RRF. Freeze text builder, labels and other ranking settings so fusion is the only change.
  4. Keep graph co-occurrence disabled until its ablation. Cap per-Agent influence, deduplicate configurations, normalise prevalence and expose dependency/permission state. Relationships cannot cross splits or become labels.
  5. Defer reranking and bundles until single-component precision, evidence and prerequisites work per type.

Artifact: qualification record, versioned configurations, paired ablation outputs and continuation decision. Acceptance requires a domain-approved measured gain without access, fabricated-ID, evidence, prerequisite or operational regression. Failure gate: disable the channel and retain incumbent; no confidence-score substitute. Handoff: R5/R6/R7 receive baseline or selected configuration lineage.

R5 — durable recommendation API and review UI, Yurii backend and Mayank UI

Prerequisites: current authorisation and retention decisions, R1/R2 result contract, mapped durable-job seam, and lexical baseline or R3 configuration that earned use. R4 is optional and cannot delay this package. Repository routes, schemas and workers are mapped after checkout reconciliation.

  1. Yurii implements one scoped service with idempotent submit, status, result and cancel operations. Server policy derives scope and rechecks every fetch and cache return.
  2. Yurii persists owned runs through approved jobs with heartbeat, restart recovery, bounded wait, cancellation, request accounting and live/replay/disabled modes. Process-local work is not durable.
  3. Mayank builds synthetic fixtures first, then frozen API UI for queued/running, assessed, lexical-only, valid empty, partial, failed, disabled, busy, unavailable and cancelled states.
  4. Mayank presents per-type evidence, assessed/conditional/insufficient-evidence state, prerequisites, truncation and lineage. Registry/diagnostics expose authorised provenance, quality and declared relationships safely.
  5. Both cover cancellation, policy change, restart and restricted records, keyboard and non-colour status access. No flow installs, attaches or executes components.

Artifact: versioned service contract, durable runs, mocks, accessible UI and operator diagnostics. Acceptance requires truthful state propagation, principal-owned retrieval, reauthorisation, restart/cancellation recovery and no hidden-record leak. Failure gate: unavailable policy/job/model/source returns typed state and blocks cohort use. Handoff: R6 receives run lineage; R7 receives configuration controls.

R6 — per-type quality decision, Yurii harness and Mayank cases

Prerequisites: frozen evaluation contract, R5 run lineage, adjudicated or explicitly unjudged cases, agreed incumbent/candidate and domain-approved per-type gates. R4 is optional: comparison may be lexical versus R3 assessment or an R4 experiment.

  1. Yurii runs the frozen final partition once for incumbent and candidate after development/validation fix retrieval, prompts, policy and fusion. The runner retains all case/configuration lineage.
  2. Mayank prepares Skills from authorised field/provenance and reviewer material, including incomplete descriptions, inaccessible Skills and non-label MCP prerequisites.
  3. Mayank prepares MCP resolved, duplicate, conflict, unknown-permission, revoked and out-of-scope cases. Yurii prevents execution or relationships becoming suitability evidence.
  4. Mayank prepares grouped Agent/card/configuration cases with noisy descriptions, access and dependencies. Yurii keeps declared Skill/MCP usage as factual context, not relevance.
  5. Reviewers settle disputes and approve partial credit before scoring. Yurii emits per-type and macro reports with unjudged outputs separate.

Artifact: Skill, MCP and Agent decision records with paired outputs, full denominators, disagreements, forbidden hits, evidence/prerequisites and operations. Acceptance requires each type to meet its own gate. Failure gate: missing labels, leakage, forbidden hits, incomplete denominator or weak type blocks promotion; result is exploratory or baseline stays active. Handoff: only complete per-type packets enter R7.

R7 — shadow, controlled rollout and rollback, Yurii and Mayank operator evidence

Prerequisites: R5 durable controls, R6 per-type decision packet, platform admission/cost/SLO approval, domain release criteria and rollback owner. R4 is optional; shadow may compare lexical baseline with R3. No configuration promotes because a date arrives.

  1. Yurii pins incumbent/candidate lineage and sends both the same admitted authorised request/candidate set. Shadow writes no user-visible result, attachment or tool execution; retention follows approval.
  2. Yurii measures states, forbidden hits, candidate/assessment coverage, citations/prerequisites, latency, attempts, tokens, cost, cache, queue and cancellation. Mayank exposes disagreements, denominators and failures.
  3. Exercise cache states, store/graph loss, timeout/truncation, restart, cancellation, policy revoke, source refresh/rollback and admission saturation. Verify revocation survives cache and technical rollback.
  4. Mayank assembles walkthrough, source/policy/configuration evidence, failure traces and cohort display. Yurii enables only named approved cohort with observation and stop conditions.
  5. Keep lexical baseline as fallback until explicit retirement. Roll back candidate on forbidden ID, unsupported evidence, actionable missing prerequisite, policy inconsistency or missed gate.

Artifact: shadow report, failure-drill receipt, cohort configuration, rollback procedure and promotion decision. Acceptance requires no safety regression and approved per-type/operational evidence. Failure gate: disable candidate/cohort, preserve truthful partial/failed states and rerun frozen evaluation after correction. Handoff: platform/domain owners receive promotion packet or documented non-promotion.
