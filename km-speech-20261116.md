# Knowledge Manager: access control and next steps (spoken update, 16 Nov 2026)

Source: a spoken update in a team call, pasted by Yurii on 16 Nov 2026. The text below is a machine transcript and was not corrected. The speaker is the project lead. Words the transcript may have misheard are listed at the end.

## Summary

| Topic | What was said |
|---|---|
| Roles | Roles are defined inside the application (Postgres) and users are mapped there. No service desk request per role. |
| Admin groups | Master or admin access still goes through the service desk. |
| Policy engine | Open Policy Agent is integrated, with simple rules: workspace scope, admin, domain owners, delegates. The application acts on its decisions. |
| Workspace creation | Reported as done and pushed to the repository. |
| Sign-in | No OIDC and no application registration in the first pass. Sign-in is LDAP based today and must be replaced by SSO through "DSP". |
| Pending now | An API with an OpenAPI spec for the roles; SSO in place of LDAP; stress testing of sign-in, roles and workspaces. |
| Later | Document classification (internal, restricted and so on), by a workflow or automatically, possibly with Microsoft Presidio. |
| Future scope | Connectors (REST, not MCP) for files, SharePoint and wiki pages; objects stored in a bucket; a pipeline from documents to a graph; separate graphs per domain, sub-domain and workspace, with governed and published content in the main graph. |

## What to test first

1. Sign-in: who gets in, who is refused, what happens when the session ends.
2. Roles: each role sees and does only what its rule allows, per workspace.
3. Workspaces: create, open, share, under many users at once.
